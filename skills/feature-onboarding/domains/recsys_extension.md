# Domain: Extending the backbone to Recommendation Systems

> **Status: unsupported design roadmap, not a turnkey extension.** This file maps *how* the
> backbone transfers to recsys and where it breaks — it does **not** yet provide the
> ranking-loss feature-evaluation machinery (NDCG-based lift, graded-relevance IV) a
> production recommender needs. Treat it as the plan to follow when recsys becomes a
> real target, and add a dedicated `references/` file at that point. Until then, the
> binary lead/credit backbone is the supported path.

Future support also requires explicit serving-query and candidate-generator semantics,
logged exposure/position policy and propensities, negative-sampling rules, per-query
ranking evaluation on frozen candidate sets, and online or counterfactual policy
evaluation. Do not treat unshown items as negatives or global IV/rank correlation as a
ranking-feature decision rule.

The 12-phase backbone was written for entity-level binary scoring (one row per
`entity × period`). Recsys differs in granularity and label structure, but the
**discipline transfers**: verify source semantics, name by behavior, check leakage,
measure incremental lift, validate out-of-time. This file maps the deltas so the
skill extends cleanly when recsys becomes a target.

---

## The granularity shift

| | Lead/credit scoring | Recsys |
|---|---|---|
| Unit of a row | `entity × period` | `user × item × context` (an interaction / impression) |
| Label | converted / default (binary) | clicked / purchased / rating (binary, graded, or implicit) |
| Feature families | entity behavior over time | **user features × item features × user-item interaction × context** |
| Primary metric | Gini / Precision@k | NDCG / MAP / Recall@k / coverage *(target state — the lift machinery for these is not yet in this skill)* |

Feature groups multiply: you now onboard **user-side**, **item-side**,
**user×item interaction**, and **context** (time, device, session) features. Each
still goes through the same phases; the cross (user×item) features are where most
signal — and most leakage — live.

---

## Point-in-time becomes per-interaction (and stricter)

In entity scoring there is one cutoff per period. In recsys **every interaction has
its own timestamp**, and the feature must reflect state **strictly before that
interaction**.

- User features (e.g. "count of past purchases", "avg rating given") must aggregate
  only events with `ts < interaction_ts`. A single global aggregation over the whole
  history leaks the future into early interactions — a pervasive recsys bug.
- This usually means **causal / expanding-window** aggregation per user, not a static
  join. The `references/leakage_and_tautology.md` timeline audit applies *per row*.

```
   user history:  e1   e2   e3   [interaction@t]   e4   e5
   allowed for features at t:  ───────────────►   (e1..e3 only)
```

---

## Leakage forms specific to implicit feedback

- **The target interaction in its own features.** If "user's items-viewed-today"
  includes the item being scored, you've leaked the label.
- **Popularity computed over the full period** (including the future) instead of
  up-to-now → leaks aggregate future demand.
- **Session leakage.** Features built from the same session that contains the label
  event often encode the outcome.

---

## Biases that act like leakage

Recsys offline data is generated by a previous recommender, so it is **not** a clean
sample:
- **Popularity bias.** Popular items dominate exposure; a "popularity" feature can
  look strong but just reproduces the old system. Check incremental lift beyond a
  popularity baseline (the recsys analogue of the redundancy/lift step).
- **Position bias.** Clicks depend on display position, not just relevance. A feature
  correlated with position partly measures the UI, not the user — analogous to lead
  scoring's "sales-touch" tautology.
- **Exposure / selection bias.** You only observe labels for items that were shown.
  Like reject inference in credit, this bounds what your IV/lift numbers mean.

---

## Offline → online gap = the recsys OOT

The credit/lead **out-of-time** check has a direct recsys cousin: offline metrics
routinely overstate online performance because of feedback loops and the biases above.
- Split by time for offline validation (future interactions held out), exactly as OOT.
- Treat a strong offline-but-weak-online feature the way you treat an
  in-sample-strong-but-OOT-weak feature: distrust it.

---

## What carries over unchanged

- Verify source semantics with formula checks (Phase 1).
- Name by observed behavior, not assumed meaning (Phase 2).
- The filter-to-lift discipline carries over, but global IV, binarized relevance, and
  rank-IC are diagnostics only; they cannot decide ranking-feature retention.
- Stability/drift monitoring (Phase 8) — arguably *more* important under feedback loops.
- Single-read / persist-one-intermediate engineering discipline (Phase 3, 10).

> When recsys becomes a real target, add a `references/` file for ranking-loss feature
> evaluation (NDCG-based lift) rather than overloading the binary IV machinery.
